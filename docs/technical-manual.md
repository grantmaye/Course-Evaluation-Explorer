# Evaluation Explorer: technical manual

Evaluation Explorer is a read-only reporting and SQL learning application. Its defining boundary is that the default **SQLite preview** and the optional **SQL Server** implementation are different engines. Learn the product rationale in the [product story](product-story.md), then use this manual to trace and modify the actual implementation.

## 1. Understand the numbers before the query

An evaluation response is one fictional overall rating from 1 to 5. A course aggregate contains a count, rating sum, and average for one institution and time range. The application has no student identity, enrollment denominator, question-level answers, or survey submission interface. Therefore response counts are not completion rates, and the numbers cannot establish teaching quality or institutional outcomes.

A weighted overall mean divides **all rating points by all responses**. Averaging course means would give a one-response course the same influence as a thousand-response course. [server/report.js](../server/report.js) uses sums and counts, and the boundary fixture in [test/report.test.js](../test/report.test.js) demonstrates 4.5 from two responses plus 3 from one response becoming an overall mean of 4, not 3.75. Empty data returns count 0, course count 0, and `averageRating: null`; zero is not a valid “no feedback” rating.

A **predicate** is a filter condition. A **sargable** predicate lets a database use search arguments directly against an index. `SubmittedAt >= start AND SubmittedAt < end` exposes a contiguous date interval, whereas `YEAR(SubmittedAt) = year` applies a function to the stored value. This can affect access paths, but does not guarantee a faster measured run. An **index** is an additional ordered data structure; a **covering index** includes the columns needed to answer the query without fetching every base row. Indexes also cost storage and write work.

## 2. Install and follow the real workflow

Use Node.js 24.15+ and npm:

```bash
npm ci
npm run demo
```

Open `http://127.0.0.1:4100`. `demo` builds with Vite then starts the Node HTTP server. Subsequent runs can use `npm start`. For hot reload, `npm run dev` starts the API plus Vite on `http://127.0.0.1:5173` with an `/api` proxy. Stop with Ctrl+C.

The default process creates 60,000 deterministic fictional rows in memory, generated by [server/data.js](../server/data.js). Restart recreates the dataset. The pseudo-random generator starts from seed 8417 and creates dates across 2023–2026, three institutions, six reusable course IDs, and a fixed rating distribution. This makes tests repeatable, not statistically representative.

Start at Northstar College/2025. Read the response count, weighted rating, and offerings with responses. Change the institution: the selected controls and loaded report are separate state; click **Run report** to apply. Query lab compares the loaded report's filters, not unsaved selections. Select 2027 and run to get the valid empty state. Walkthrough points to the code layers. The existing sidebar, typography, colors, and responsive report remain the project's distinct interface.

## 3. Architecture and file map

```text
React controls → GET /api/report → parseFilters → timedQuery(store)
  → SQLite prepared statement OR SQL Server typed stored procedure
  → present(rows) weighted summary + course labels → React table
```

| Source | Responsibility |
| --- | --- |
| [src/App.jsx](../src/App.jsx) | Filter versus applied state, abort controllers, error/retry, report, Query lab |
| [src/styles.css](../src/styles.css) | Responsive visual identity |
| [server/index.js](../server/index.js) | Driver selection, loopback listener, shutdown |
| [server/app.js](../server/app.js) | GET routes, error mapping, static files, no-store API responses |
| [server/report.js](../server/report.js) | Strict filters, weighted presentation, comparison protocol |
| [server/sqlite.js](../server/sqlite.js) | Synchronous in-memory preview, fixtures, prepared queries |
| [server/mssql.js](../server/mssql.js) | Encrypted connection settings, pooling, typed calls |
| [sql/schema.sql](../sql/schema.sql) | SQL Server table, constraints, covering index |
| [sql/report.sql](../sql/report.sql) | Baseline and range procedures |
| [scripts/setup-sqlserver.mjs](../scripts/setup-sqlserver.mjs) | Restricted disposable database setup and seed |
| [sql/measure.sql](../sql/measure.sql) | Manual SQL Server CPU/IO/plan investigation |
| [vite.config.js](../vite.config.js) | React build and development proxy |

The HTTP app receives a store instead of constructing a database itself. That adapter boundary lets tests use a tiny SQLite fixture or a deliberately failing store. React aborts outdated requests when a report is rerun or the component unmounts; the server still may finish an already issued database call. Report and comparison errors have a visible retry path.

## 4. Schemas and API contracts

`dbo.EvaluationResponses` contains ResponseId (integer primary key), InstitutionId (integer constrained 1–3), CourseOfferingId (integer), SubmittedAt (`datetime2(3)`), and Rating (tinyint constrained 1–5). There are no institution/course foreign-key tables in this simplified model. Course names are application fixtures. SQLite uses the same conceptual columns but stores timestamps as canonical ISO UTC text; lexicographic range comparison relies on that format. Arbitrary locale-formatted date strings are outside its input contract.

The SQL Server index keys are `(InstitutionId, SubmittedAt)`, with `(CourseOfferingId, Rating)` included. SQLite approximates coverage by putting all four columns in the index; it does not execute SQL Server's INCLUDE syntax or T-SQL procedures.

| Endpoint | Response/behavior |
| --- | --- |
| GET /api/meta | institutions, active engine label, startup totalResponses |
| GET /api/health | process/store engine identity; not a fresh database ping |
| GET /api/report?institutionId=1&year=2025 | rows, weighted summary, normalized filters, engine, durationMs |
| GET /api/compare?institutionId=1&year=2025 | sameResults, baselineMs, rangeMs, samples=5, engine |

Missing filters default to institution 1/year 2025. Institution must be the single character 1, 2, or 3. Year must be four digits from 2000 through 2099. Invalid filters return 400. Unknown API routes return 404; non-GET methods return 405. Adapter failures return a generic 500, while diagnostic details go to the server log.

```bash
curl -s 'http://127.0.0.1:4100/api/report?institutionId=1&year=2025'
curl -s 'http://127.0.0.1:4100/api/compare?institutionId=1&year=2025'
curl -i 'http://127.0.0.1:4100/api/report?institutionId=4'
```

The first returns course rows; the second returns measured comparisons; the third returns 400. All API responses use no-store caching. Neither selecting an institution nor supplying a query parameter proves authorization. This local demo has no authentication.

The range procedure accepts `@InstitutionId int`, `@StartDate datetime2(3)`, and `@EndDate datetime2(3)`. The baseline accepts institution and year. Values are bound explicitly with `mssql`, not interpolated into query text. Both group and order by CourseOfferingId, use `COUNT_BIG`, sum ratings cast to bigint, and average ratings cast to decimal to preserve fractions. Date ranges include the start and exclude the next year's start: midnight on January 1 belongs to exactly one year.

## 5. What Query lab measures and proves

[compareQueries](../server/report.js) warms each variant once, then records five calls per variant with alternating order. It returns the median of each group, measured with `performance.now()` around the adapter call. That duration includes database work, scheduling, and transfer; it is not SQL CPU time or logical reads. Both variants use the same existing index.

Every one of the ten measured result sets must agree with the first measured result on ordered course IDs, counts, exact sums, and average within 0.000001. Earlier mismatches can no longer be hidden by a matching final pair. The warmups are not part of correctness comparison. A changing external database may produce a mismatch even when predicates are equivalent; comparisons do not run in one snapshot transaction. Investigate data stability before blaming SQL.

In SQLite the function predicate uses `substr(SubmittedAt, 1, 4)`, not YEAR. Results matching in SQLite does not demonstrate SQL Server plans. Use [sql/measure.sql](../sql/measure.sql) with actual execution plans enabled in a SQL client for SQL Server evidence. Repeat across institutions/years; never clear production caches for a portfolio demo. No timing threshold is asserted by tests because runtime noise is expected.

## 6. SQL Server setup and environment

Copy [.env.example](../.env.example) to `.env` and replace placeholders only in that ignored local file:

| Variable | Meaning/default |
| --- | --- |
| DB_DRIVER | sqlite by default; mssql opts into SQL Server |
| PORT | HTTP listener, 4100 by default |
| SQL_HOST / SQL_PORT | Database address; localhost / 1433 defaults |
| SQL_DATABASE | EvaluationDemo; setup allows an optional `_Alphanumeric` suffix |
| SQL_USER / SQL_PASSWORD | Database identity; sa default user, password required in mssql mode |
| SQL_ENCRYPT | Encryption enabled unless exactly false |
| SQL_TRUST_CERTIFICATE | Verification bypass only when exactly true; local self-signed development only |
| E2E_PORT | Playwright listener port; default 4100 |

Use a disposable SQL Server 2022+ instance. `npm run db:setup` retries initial connection while a container starts, creates the restricted database if absent, installs schema/procedures, and bulk-seeds only when the table is empty. Seeding is transactional. Setup is not a reset command and does not reconcile partially populated or intentionally modified fixtures. Use a new disposable database name for pristine integration tests.

```bash
npm run db:setup
npm run test:sqlserver
npm run demo
```

Setup requires database/schema creation permissions. A separate runtime account could have EXECUTE on the two procedures and SELECT for the metadata count. The connection pool permits four connections, with 5-second connection and 15-second request timeouts. SQL Server configuration is server-side; nothing requires a browser database password.

No local SQL Server is required for the preview. The repository CI provides a Linux SQL Server service. If local Docker/SQL Server is unavailable, record that limitation and check the real CI SQL Server job; do not call SQLite a substitute. The metadata count is captured at store startup, so external database changes can make that label stale. Health reports the selected engine and does not establish continuing database connectivity.

## 7. Tests and failure laboratories

```bash
npm test
npm run build
npx playwright install chromium
E2E_PORT=43128 npm run test:e2e
npm run test:sqlserver   # requires disposable seeded SQL Server configuration
```

Playwright always starts its own SQLite server, and never reuses an unrelated process on the selected port. The application has no configured lint or TypeScript check; JavaScript syntax, API/unit behavior, Vite compilation, browser behavior, and SQL integration are the relevant current checks. [.github/workflows/ci.yml](../.github/workflows/ci.yml) separates application and SQL Server jobs. A workflow file alone is not evidence of success: inspect the run for your commit.

### Lab A: filter and date boundaries

Run `node --test --test-name-pattern='range includes start' test/report.test.js`. The six-row fixture includes the first and last millisecond of 2025, next year's midnight, the previous year's last millisecond, and another institution. Expected: course 101 count 2/sum 9/mean 4.5, course 102 count 1/sum 3/mean 3, overall mean 4. This demonstrates exclusive end boundaries and weighted averaging together.

### Lab B: wrong comparison that looks correct at the end

Run `node --test --test-name-pattern='comparison checks|comparison detects' test/report.test.js`. One adapter returns a wrong first measured rating total; another returns an empty intermediate result. Final calls agree in both cases. Expected: `sameResults` stays false. The first test also verifies the exact warmup and alternating call order. This protects the meaning of the green Results match badge.

### Lab C: unavailable report and recovery

The browser test intercepts `/api/report` with a 503, expects an accessible error alert, restores the route, and clicks Run report. Expected: Feedback by course becomes visible again. The API failure test throws an internal adapter error and checks a generic 500 response without the diagnostic. In a real SQL Server failure, check the server log, host/port, credentials, database existence, and procedures. Do not disable TLS verification as a general fix.

### Lab D: empty reports and rejected inputs

Select 2027 and run the report. Expect zero counts and a dash for the null mean, with a useful empty-state message. Call the report with `year=2025junk` or `institutionId=1%20OR%201%3D1`; expect 400 before any query. This validation is additional to parameter binding, not a replacement for it.

### Lab E: prove the T-SQL path

Run `npm run test:sqlserver`. The first test independently aggregates the generated 60,000 rows in JavaScript for three institutions and four years, checks SQL results, and compares both predicates. The second inserts date-boundary rows inside a transaction, checks the fractional mean and isolation, then rolls back. A reversed date interval must throw the procedure's validation error. Do not run this against a real institutional database; it assumes the disposable fixture.

## 8. Maintenance, tradeoffs, and exercises

The SQLite adapter is synchronous and blocks Node's event loop. That is convenient for a bounded local dataset but inappropriate for a busy public reporting service. SQL Server calls are asynchronous and pooled. The frontend and fixture catalog share conceptual course IDs without generated schema contracts; keep both adapters' aggregate result shape consistent.

1. **Add a course.** Update the course catalog and fixture generator, then add a fixture report assertion. **Solution:** preserve unique IDs, verify present() adds its correct label, and ensure both SQL adapters group the new ID identically. Avoid silently changing institution semantics or claiming enrollment rates.
2. **Add a term filter.** **Solution:** define precise UTC start/end boundaries, extend validated API inputs and typed SQL parameters, update SQLite queries and UI, and add boundary tests. Retain the half-open interval instead of “23:59:59” hacks that fail with precision changes.
3. **Make comparison snapshot-consistent.** **Solution:** decide whether concurrent writes are allowed, then execute both variants under an appropriate database snapshot/transaction policy. Do not suppress mismatches. Document isolation cost and compare equivalent data before comparing duration.
4. **Add response percentages.** **Solution:** first model eligible enrollment and submission uniqueness. Counts alone cannot produce a valid completion-rate denominator. Add authenticated institution access and privacy rules before real student data.

## 9. Interview questions and answers

**Why cast before AVG?** SQL integer aggregation can lose fractions. The decimal cast preserves the intended rating mean; tests require 4.5 at a timestamp boundary.

**Why not average course averages?** Course sizes differ. Sum rating totals and divide by the total response count.

**Does the index guarantee a speedup?** No. Selectivity, plans, caching, statistics, transfer and noise affect timings. Query lab demonstrates a measurement protocol, not a universal result.

**Is institution filtering multitenant security?** No. Any caller can choose any fixture institution. Production authorization must derive allowed scope from a verified identity.

**What do the two engine tests prove?** SQLite tests validate the preview and HTTP behavior. SQL Server integration executes the actual stored procedures and compares independent expectations. Neither establishes production-scale performance.

**What is the hardest maintenance invariant?** Preserve equivalent date/filter semantics and weighted results across both engines while honestly reporting what the measurement means.

## 10. Dependency limitation

The source-map-js patch resolves the high-severity build dependency advisory. As of 2026-10-07, npm still reports three moderate entries for the `mssql → tedious → sprintf-js` chain. The [upstream sprintf-js advisory](https://github.com/advisories/GHSA-hp3w-g68c-fv3c) lists no patched release. The inspected tedious calls use fixed format strings; application filter input is validated and passed as typed SQL parameters. That reduces the observed exposure but is not a clean audit result or a general security guarantee. Do not run `npm audit fix --force`: its suggested mssql 4.2.0 downgrade is outside the compatible patch scope. Recheck upstream releases before external exposure. See [SECURITY.md](../SECURITY.md).
